# 基准测试的缓存场景（前缀缓存 / KV 复用）

同一个模型、同一段 prompt，首 token 延迟（TTFT）能差几十倍 —— 差的不是硬件，是服务端
**有没有复用上次算过的 KV**。命中时 1M 上下文的首 token 可以几十毫秒出来，不命中就是老老实实
把整段 prompt 算一遍（几十分钟）。所以只报一个 TTFT 数字，等于把两种完全不同的工况混在一起：
长上下文扫描里最容易被它骗，看到的"这模型长上下文好快"往往是缓存热着的假象。

测速页的**缓存场景**就是把这个变量单独拎出来测：

| 场景 | prompt 形态 | 回答的问题 |
| --- | --- | --- |
| 冷启（不命中） | 每请求换一个**全新前缀**（唯一标记放在最前面） | 真实 prefill 成本是多少 |
| 部分命中 | 共享 90% 前缀 + 每请求自己的新尾巴 | 多轮对话里只有新增内容要算，能省多少 |
| 完全命中 | 与预热**逐字相同**的那段 | 缓存的上限：整段 KV 复用 |

三种场景的 prompt 长度一致（都等于目标档位），差别只有前缀新不新 —— 对比的才是同一档位下的
缓存差异。界面的「缓存命中对比」给出 `倍数 = 冷启 TTFT ÷ 命中 TTFT`；llama.cpp 还会自报
`timings.cache_n`（直接复用、没有重算的 prompt tokens），界面显示成"服务端复用 N% 输入"，
这是"到底命中没有"的权威答案，不靠推理。

> 默认三种都测，所以每个档位跑三遍。只测命中会得到偏乐观的数字，只测冷启又看不到缓存收益 ——
> 缓存的价值恰恰在差值里。跑 1M 这种贵的档位时可以只勾一种。

## 什么场景会**不**命中

按"最常踩"排序，前三条是本地部署里出现频率最高的：

1. **前缀里有每次都变的内容**。前缀缓存是按**最长公共前缀**命中的，第一个 token 就分叉的话
   后面整段都用不上。典型杀手：
   - 系统提示里注入当前时间 / 日期（本仓库的对话就是这么做的：`chat.ts` 的
     `currentTimeSystemMessage()` 每轮把"今天是几号"拼进 system 消息）——云端的隐式缓存
     （OpenAI / Anthropic / DeepSeek）对聊天场景因此几乎永远不命中；
   - 每轮重新排序的工具列表、随机 id、请求级的 nonce、`temperature` 之外的随机种子字段；
   - 对话历史从头重排（把最新消息放到最前、或做摘要压缩时改写了前面几轮）。
2. **llama.cpp 的 KV 是每个槽位各自的**。`--parallel N` 下同一个 prompt 并发发 N 份，
   它们大概率落在不同槽位上 —— 只有第一个请求是冷的，其余也**不会**互相命中
   （除非开了跨槽共享缓存）。顺序重发（先发一遍再用同样内容测）才稳定命中，
   这也正是"完全命中"档先预热一遍的原因。
3. **`--parallel` 还会把窗口切小**。`SERVER_CTX_SIZE` 是 KV 总量，被槽位数均分：并发 4、窗口
   32k 时单请求只有 8k。窗口变小 → 前缀被挤出缓存 → 命中率跟着掉。
4. **引擎的缓存开关**。vLLM 的自动前缀缓存（APC）按 16 token 块对齐，块没对齐的部分不算命中；
   SGLang 的 RadixAttention 才会做前缀树级的复用；部分推理框架（含某些厂商的打包版）默认关闭
   prefix caching，需要显式打开。
5. **缓存被挤掉**。KV 显存有限，比当前 prompt 更长的旧请求会把前缀从缓存里顶出去；
   服务端重启、换模型、换量化版本同理。
6. **云端 API 的隐式缓存有自己的规矩**：要求前缀完全一致、有 TTL（常见 5~60 分钟）、
   有最小长度（如 1024 tokens 起）、按服务商 / 账号隔离，而且不保证一定命中。
   跨账号、跨区域、跨版本都可能落空。
7. **token 序列变了但文字看着没变**：改 chat 模板、换 tokenizer、升级引擎版本、
   系统提示末尾多一个空格或换行 —— 文本差异看不出来，token id 已经全变了。
8. **多副本 / 多卡路由**：请求被分到另一台机器或另一个 GPU worker 上，本地缓存不共享。

## 怎么判断"到底命中没有"

三种证据，从强到弱：

1. **服务端自报**：llama.cpp 的 `timings.cache_n`（界面里的"服务端复用 N% 输入"）。
   这是唯一能直接看到"复用了多少 tokens"的数字。
2. **冷启 vs 命中的 TTFT 倍数**：×10 以上说明缓存生效；**×1 附近说明服务端根本没吃到缓存**
   —— 界面会直接把这条写成提示（"常见原因：并发槽位各自的 KV / 前缀里有每次都变的内容 /
   引擎没开缓存"），CLI 也会打一行。
3. **prefill 吞吐**：命中时它不应该再随档位上升（几乎全部 token 直接复用）。

## 命令行

```bash
omi benchmark --contexts 32k --cache cold,warm     # 只比缓存
omi benchmark --contexts 8k,32k,128k,1m            # 三种场景都测（默认）
omi benchmark --contexts 1m --cache cold --gen 64  # 只测 1M 的真实 prefill
```

`--cache` 取 `cold` / `partial` / `warm`，逗号分隔；不传就是三种全测。

## 实现要点（改这块代码时先看）

- prompt 由 `bun/benchmark.ts` 的 `buildPromptFor()` 生成：冷启的唯一标记在**最前面**
  （放结尾会变成"整段可复用"，那就不是冷启了），部分命中把标记放在 90% 之后。
- 预热内容按场景挑：完中命中发**完全相同**的一段；部分命中只发共享前缀（把前缀填进缓存，
  测量请求的新尾巴仍然要现算）；冷启只发一小段探针（拿正文预热毫无意义）。
- 并发批次里的每个请求都带**各自**的唯一标记，否则同批的第 2 个请求会命中第 1 个。
- 服务端不报 `cache_n` 时（vLLM / SGLang 的 OpenAI 兼容流里没有）复用比例留空，
  界面靠 TTFT 差值给结论 —— 不猜一个数出来。
- 汇总的「平均 / 最佳」只取**一种**工况（有冷启就取冷启，否则取命中）：两者混着平均，
  得到的数字谁都不像。
